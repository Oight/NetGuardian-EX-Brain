## 1. 建议本轮确定的方向

| 编号 | 拟采用的修订方向 | 对范围的影响 |
|---|---|---|
| R1 | 将作品定位为接入现有 Wazuh 的受限客户端辅助工具 | 从原始日志处理平台收缩到可见告警的调查与解释 |
| R2 | 实际部署分别描述学校平台、使用者电脑、teleagent 服务所在环境 | 不再用“全部本地服务”概括实际应用 |
| R3 | 用 Node.js 本地应用核心承接客户端业务 | 重新划分原 Python 服务、页面、任务与供应商适配器的职责 |
| R4 | 为本地 TeleAgent 会话后端增加独立适配，优先验证桌面宿主接入 | 利用其实际 Agent 循环与 MCP 能力；不将其当作普通模型补全接口 |
| R5 | 将原始日志导入、Wazuh 安装和规则配置移入实验环境附录 | 这些操作不成为使用者客户端的权限或必需操作 |
| R6 | 按账号实际可见的数据重新定义功能条件与缺证据行为 | 无权访问、未采集、未索引等限制不能用服务器文件读取补齐 |
| R7 | 保留证据追溯、案件版本、有限调用和人工确认 | 按新部署边界调整实现位置，避免重复建设 teleagent 已有能力 |
| R8 | 重新编排验收与工期 | 以接入可行性、使用任务和模型增益为先，不继承原吞吐和工时承诺 |
| R9 | 将释放出的开发范围用于客户端调查、证据呈现和核查跟进 | 首版形成一条下游工作闭环，其他扩展分阶段评审 |

已经确定的前提：竞赛作品需要参考真实应用；客户端以 Wazuh 受限账号工作；客户端采用 Node.js；需要对接 teleagent API。

新补充的依据：TeleAgent 2.7.0 的本机后端 API 已有独立实例的模拟模型/MCP 验证，以及已登录桌面实例的真实文本对话验证，详见第 6、10 节。旧研究设计里的自研采集与规则职责不随这些接口结论一起引入，以当前 Wazuh 受限接入前提为准。

尚未确认：Wazuh 账号实际可用的接口和数据范围、客户端界面形态、稳定的桌面认证桥接，以及真实模型、专用 Skill、受限 MCP 与 Wazuh 的项目链路。赛事对具体集成和展示方式的要求仍需按正式材料核对；“比赛由该产品相关方举办”不直接等于任意嵌入或分发方式均满足要求。

## 2. 先补部署与权限边界，再改功能流程

拟将原第 1、3、8 节重写为“实际应用部署”和“实验部署”两个部分。正式修订时需要给出部署图、职责表、数据流向，以及每条跨环境连接所需的账号或访问条件。

### 2.1 实际应用中建议采用的职责分配

以下是供审阅的部署取向，具体地址、端口与运行方式留待接口核实后确定。

| 运行位置 | 放置内容 | 需要明确的边界 |
|---|---|---|
| 学校已有的受监测主机、设备 | 原有 Wazuh Agent 或其他既有日志来源 | 由学校维护；与本项目的研判 Agent 区分命名 |
| 学校已有服务器环境 | Wazuh Manager、Indexer、Dashboard，以及已有采集、转发、规则和留存配置 | 本项目客户端不取得主机管理权，不负责安装或改造这些组件 |
| 使用者电脑：Node.js 本地应用核心 | Wazuh 连接、查询限制、告警投影、案件组织、证据快照、TeleAgent API 适配、结果校验、本地任务状态 | 只通过约定接口使用当前账号权限；不读取学校服务器文件系统 |
| 使用者电脑：本项目的 MCP 适配 | 将本地调查业务和获准 Wazuh 查询作为有限工具提供给 TeleAgent | 复用同一业务核心与访问检查；工具不会自行派发另一轮 Agent 任务 |
| 使用者电脑：界面部分 | 连接状态、告警与案件、调查过程、引用、反馈和报告 | 具体采用桌面界面或本地 Web 界面待定；原始凭据不进入模型上下文 |
| 使用者电脑：应用数据目录 | 必要的案件记录、有限证据缓存、任务与反馈 | 不复制全校日志；区分平台实例和用户，规定留存、退出登录及账号切换后的访问行为 |
| 使用者电脑：TeleAgent 桌面宿主及其 Go 后端 | 由原宿主管理登录与运行环境；本项目通过本机签名 API 创建、提交、跟踪和取消调查会话 | 这是优先联调候选；认证桥接仍待产品化验证，实际端口不硬编码 |
| 配置指定的外部模型与审查服务 | TeleAgent 调用的模型及相应审查能力 | 本地运行 Agent 后端不代表模型、审查或所有数据留存均在本机；按实际配置核实流向 |

“Node.js 本地应用核心”指业务执行位置，不预先选定 Electron、数据库驱动或界面框架。如采用桌面应用，界面与本地核心通过明确的受限通道交互；如采用本地 Web 应用，也需明确本地服务的访问边界。

建议首版只承诺使用者主动调查，以及应用运行期间明确开启的有界刷新。客户端关闭、休眠或离线期间，不承诺持续监测。全天候调度和多人共享案件需要另外的服务部署与权限前提，列为后续审阅事项。

该部署方向对应两条链路：Node.js 客户端经本机 API 委托 TeleAgent 执行调查；TeleAgent 经本项目 MCP 回到同一业务核心查询证据，由业务核心以受限账号访问学校 Wazuh。MCP 查询结果返回当前会话，不触发“查询 → 新会话 → 再查询”的递归派发。

### 2.2 实验部署的修订原则

可以继续用笔记本或虚拟机模拟学校服务器，但 Wazuh 与客户端之间仍通过受限接口交互。实验准备者负责导入数据和配置 Wazuh，客户端运行账号只负责读取获准内容；两者凭据与目录权限分开。

公开原始数据、PCAP、标签、导入脚本及规则配置属于实验准备环境。客户端不能通过共享目录或额外挂载绕过 Wazuh 接口读取它们。已有告警若进入实验索引，需要单列该索引及权限，不能据此声称标准部署一定提供同样数据。

## 3. 新增“接入能力与功能条件”一节

受限账号并未具体说明接口能力。Wazuh 的面板、Indexer 查询接口和 Server 管理接口承担不同职责；能够登录面板，不足以证明独立客户端能直接访问所需接口。[官方架构与通信说明](https://documentation.wazuh.com/current/getting-started/architecture.html)

因此，正式设计需要先列出下表，并用现有授权做接入核实。无需为了探测能力尝试写入、越权或读取其他范围。

| 需要核实的能力 | 对应修订要求 |
|---|---|
| 查询入口、认证方式、网络可达性、证书信任 | 明确可供客户端调用的入口；不从面板登录自动推导 API 访问权 |
| 获准索引、设备或群组范围、可见字段与时间范围 | 所有查询、统计、案件和报告都带有可见范围说明 |
| 搜索、分页、排序、计数或聚合是否可用 | 不可用的操作不能成为必需流程；部分结果不能声称完整 |
| 成功与失败认证背景是否实际可查 | 决定能否开展“失败后成功”的补证，不能只依赖规则告警推断 |
| 资产、主机属性与业务信息是否可用 | 只使用能获取且来源清楚的信息；负责人和重要性缺失时保留未知 |
| 身份过期、账号权限变化、限流与接口不可达 | 分别描述恢复或降级方式，不改用本机文件或管理凭据兜底 |

告警检索优先核实 Indexer API；Server API 只用于已获授权且确有需要的资源查询。官方文档分别说明了告警索引查询与 Server API 的权限控制，正式修订不能把两者统称为一个“Wazuh API”。[告警查询](https://documentation.wazuh.com/current/user-manual/indexer-api/use-case.html)、[Server API 权限控制](https://documentation.wazuh.com/current/user-manual/api/rbac/index.html)

只读权限也可能覆盖过大的范围，应记录实际获准资源，不照搬示例中的全索引授权。[官方用户与角色映射说明](https://documentation.wazuh.com/current/user-manual/user-administration/rbac.html)

如现有条件只能使用面板、没有已确认的程序化查询方式，接入前提应标为未满足。审阅时再决定是否请求已有查询接口的有限授权，或单列人工导出模式；不默认增加服务器插件、转发程序或面板抓取方案。

查询返回零条，只能说明本次可见范围内未返回匹配记录。无权访问、查询失败、部分分页、来源覆盖未知与完整查询后未发现匹配，应在设计中分别表达。

## 4. 因 Wazuh 引入而需要重新分工的环节

拟把以下处置表加入修订记录，防止只把 Python 改名为 Node.js 后继续沿用旧流程。

| 原设计环节 | 建议如何修订 | 修订时需要说明的内容 |
|---|---|---|
| 原始日志采集、tail、混合格式识别 | 移至学校已有平台或实验准备附录 | 客户端只适配已获准的查询响应 |
| Windows/Linux/设备原生格式解析 | 从客户端主流程移出 | 仍需统一告警字段视图，但不重复编写原始日志解析平台 |
| 原始事件归一化和隔离队列 | 改为查询结果投影与质量标记 | 保留原字段与平台引用；响应不兼容时明确报告 |
| 自研认证计数、检测状态机 | 取消客户端默认原始检测职责 | 利用现有告警开展调查；不把已有规则命中算成作品新增检测能力 |
| 配置 Wazuh decoder、频率规则和基础认证输出 | 移为实验准备或明确的可选平台变更 | 实际接入不默认拥有配置权；额外规则必须单列部署要求 |
| “失败后成功” | 改为有条件的上下文查询 | 必须能读取相应背景，并说明账号、目标、顺序与查询覆盖情况 |
| 网络告警调查 | 保留可见告警的解释和补证 | 缺少完整流记录时，不承诺精确扫描基数或连接基线 |
| 全量证据服务、源端文件回查 | 改为远程受限检索加必要的本地快照 | 快照是查询时取得的内容；原文只在获准响应实际包含时可用 |
| Kafka、Vector、Filebeat | 从客户端必需组件中移出 | 学校既有链路可继续存在，但由平台维护 |
| 实验资产 CSV | 改为平台可见资产信息优先，其他来源可选 | 额外导入或人工补充需标来源、时效和适用范围，不能作为默认已知事实 |
| 供应商模型 API worker | 改为本地 TeleAgent 会话适配与本地结果处理 | 首版由 TeleAgent 使用其已登录模型路径，不额外建设并行的直接模型调用主线 |
| 双优先级 | 保留区分调查与拟处置的意图，重新核对条件 | 资产重要性和影响未知时，相应策略不能假定数据齐全 |
| 案件、证据版本、引用校验、人工反馈 | 保留并迁移至 Node.js 客户端职责 | 本地事实与模型推断区分；旧结果不能覆盖新证据 |
| 自动封禁、规则发布、平台告警关闭 | 继续排除在受限客户端首版之外 | 人工反馈先保存在本地，不暗含对 Wazuh 的写入能力 |

## 5. Node.js 客户端需要补写的设计内容

本轮建议迁移的是运行职责和业务约束，不逐项照搬旧技术选型。

| 旧实现假设 | 后续设计需要给出的修订内容 |
|---|---|
| Python/FastAPI 服务加 Jinja 页面 | Node.js 本地核心、界面与二者通信边界；界面形态确认后再选择具体框架 |
| Pydantic 负责契约校验 | 保留运行时输入输出校验要求，后续确定 Node.js 校验方案；不能只依赖静态类型 |
| httpx 与模型供应商适配器 | Wazuh、teleagent 两个连接适配，分别处理认证、超时、取消和错误 |
| SQLite 保存任务、案件与反馈 | 保留必要持久状态，核对 Node.js 打包和运行兼容性后再定存储库 |
| 供应商单次调用结果即研判结果 | 根据 teleagent 的会话、任务、消息或流式结果语义重划提交与完成时点 |
| 后端常驻，持续自动消费 | 明确客户端启动、退出、休眠、断线和重新打开后的行为 |

凭据由本地核心管理，模型只收到获准发送的业务材料。正式设计应补充有限查询工具的执行边界，避免把任意查询、Shell 或服务器文件读取作为模型工具。为本项目任务显式配置所需工具范围，并核对当前版本的权限行为，不依赖通用办公 Agent 的默认全部能力。

已有研究支持由 TeleAgent 经 MCP 提出补证请求。建议把“应用主动发起调查 + 专用 Skill 指导步骤 + MCP 按需补证”作为目标接法；真实项目链路尚需联调。联调期间可先提交冻结证据包验证文本路径，但该路径单列为阶段成果，不能代替工具调查演示。

业务层只承诺清楚的案件、证据与结果契约；TeleAgent 的版本、认证和消息格式变化集中在适配层处理。此处保留替换边界，不扩展成首版必须实现的多平台框架。竞赛演示应如实显示是否实际使用 TeleAgent，不能静默换用其他模型后仍计为平台集成。

## 6. 用已有研究具体化 TeleAgent 接入修订

### 6.1 已有结论及其证据边界

下表依据 2026-10-18 对 TeleAgent 2.7.0 的报告。本轮只读研究材料，没有重新执行探测，以下结论不推广到所有版本。

| 已有研究结论 | 验证边界 | 对设计的修订要求 |
|---|---|---|
| 桌面宿主管理本机 Go 会话后端；API 使用本地签名认证 | 独立实例和已登录桌面实例均有调用记录 | 区分 Wazuh 凭据、本机 API 签名凭据、TeleAgent 模型账号登录三种职责；不把它画成单一云端模型 API |
| 创建会话、异步提交、消息查询、SSE、中止已有独立实例验证 | 已登录桌面实例完成真实文本轮次；工具链验证使用模拟模型和审查服务 | 分别验收传输、真实模型对话与真实工具调查，不合并为“项目链路已完成” |
| 不存在的会话提交也可能得到 HTTP 204 | 独立实例实测 | 先确认会话创建，关联用户消息与助手回复，再检查完成字段、结束原因和错误；204、idle 或已有文字均不能单独表示业务完成 |
| 任意自定义 messageID 曾干扰循环判断 | 独立实例实测 | 业务 job_id 独立保存，映射后端生成的会话和消息 ID，不复用为任意消息 ID |
| 本地 MCP 调用及结果进入下一轮模型请求已跑通 | 使用合成证据、模拟模型及模拟审查；真实模型加专用 MCP 尚未完整验证 | Node.js 业务层增加有限 MCP 工具；优先验证真实模型能调用和引用实际返回的证据 |
| 所分析 MCP 适配路径处理普通 content 文本；存在工具输出截断 | 二进制分析；模拟工具链已验证文本路径，不能据此保证所有边界值 | 返回有界的文本 JSON、摘要与证据 ID；不只返回 structuredContent，不一次倾倒大量日志 |
| MCP 调用还涉及平台审查服务配置 | 隔离测试中曾因缺少配置失败；后来使用模拟服务跑通 | 真实联调核对审查服务与相应授权，不把测试用模拟放行方式纳入实际接入 |
| 跨会话记忆偏向个人画像，由桌面端另行整理 | 静态分析与八项合成回放；没有完整业务事实保存保证 | 案件、证据、审核和近期事件状态保存在本项目；不以 TeleAgent 个人记忆充当事件库 |
| 步数提示和内部重试不能直接等同于硬调用预算 | 静态分析，部分强制边界未确认 | 应用自行限制调查查询量与有效期；记录中止请求、后台是否真正结束以及可获得的用量，不能保证已发生的外部费用被撤销 |
| 一次真实文本测试记录输入 10498、输出 430 tokens | 单次合成案例、通用主 Agent；非安全任务质量或成本基准 | 预算包含宿主提示、工具和历史开销；重新测量专用调查配置，不沿用“业务证据包大小就是总输入”的估算 |

### 6.2 需要选择的宿主接入方式

优先联调候选为“保留用户已登录的 TeleAgent 桌面宿主，Node.js 应用调用其本机后端”，因为已有真实对话证据。正式修订要补充明确、可维护的认证桥接，以及宿主重启、升级、账号切换和退出后的恢复行为。

报告中的只读进程环境访问证明了获授权的研究连通性，不应直接写成用户安装客户端后的默认凭据获取机制。当前材料未证明存在稳定公开的第三方凭据接口。

“由本项目自行启动随包 Go 后端”保留为备选评估项：独立实例已有模拟链路证据，但还需承担登录、配置、工具环境和维护等职责，并核对分发与参赛方式。暂不把它升级为首版额外开发主线。

### 6.3 后续设计需要补齐的状态与结果约定

本地记录案件、输入快照、业务 job_id 与 TeleAgent session_id、用户消息 ID、结果消息 ID 的映射。SSE 用于进度展示，消息回读用于核实对应结果；完成条件需要同时检查消息关系、正常终结、错误与业务结果校验。随包 OpenAPI 与实测存在差异，例如 GET /agent 实测 404，接口表以核实结果为准。

同一案件首版只允许一个活动调查，用户追加问题和证据更新明确排队或取消后再启动。重连优先核实原任务，不能默认异步提交自带幂等性；自有重试与平台内部重试分别记录。

应用的证据引用范围应受案件及输入版本约束。补证取得新材料时登记来源、查询范围与取得时间，再形成显式的新证据版本；模型不能悄悄把“当前所有可见内容”混为一次冻结输入。

正式设计需要核实项目工作区会加载哪些提示、指令和历史记忆。关闭自动记忆整理不等于旧记忆必然不再注入；不能仅凭新建会话就声称完全隔离个人上下文。专用提示与工具限制需要通过实际请求和行为验证。

原文的固定 30 秒、两次尝试、每日 50 次及输入输出 token 参数改为待测配置。保留有限调用和费用约束的要求，具体数值按实际宿主、模型、审查服务与任务耗时重新确定。

## 7. 重写用户任务、功能条件与验收

### 7.1 先固定一个可以核实价值的使用任务

建议后续设计先描述：使用者在 Wazuh 中遇到一组正在发生或刚发生的可疑告警，在客户端建立调查案件；助手按需查询账号可见的证据，与使用者核对假设和缺口，形成可引用的调查意见及下一步核查事项；使用者确认和记录处理情况，必要时再以新增可见证据复核。

这一任务是修订的候选主线，需要用访谈或经授权的案例确认。“高校”需要落实到具体使用者、核查步骤及结果交接对象；未获得依据时，不补写校园特有能力或节省工时结论。

首版建议先由用户选择告警或明确的时间范围发起调查。后台自动筛选和轮询作为可单独开启的功能，不继承原每两秒轮询及全天候检测承诺。

### 7.2 新增客户端下游扩展的取舍

Wazuh 承担采集和初筛后，客户端仍需要查询响应适配、可见范围处理和证据组织；这些工作不能全部删除。释放出的开发范围建议优先投入下表。P0 项共同构成一条最小工作流，P1 在该工作流可用后再扩展。

| 扩展方向 | 建议优先级与范围 | 能提供的新增价值 | 数据与权限条件 |
|---|---|---|---|
| 案件与证据工作台 | P0：选择一组告警、形成时间线、查看原依据，支持人工修正归并 | 将平台观测、模型解释、人工判断放在可比较的位置；不再只多展示一份文字报告 | 仅处理已获准的告警和快照；归并不等于已证明同一攻击链 |
| 交互式调查助手 | P0：围绕当前案件追问、提出补证问题、调用有限 MCP 查询并解释结果 | 让 Agent 实际参与“下一步查什么、查到后如何改变判断”；界面显示工具和证据进度 | 模型不持有 Wazuh 凭据，不决定扩大账号权限；查不到就显示缺口 |
| 核查清单与处理记录 | P0：生成可编辑的核查事项或交接草稿，保存人工确认和处理备注 | 调查结果能够转化为使用者接下来的工作，报告完成与案件解决分开 | 首版仅本地记录或导出；不自动派单、发消息或对平台执行处置 |
| 新证据与结果差异 | P1：应用运行期间按需刷新，展示新增、冲突与原结论的覆盖范围 | 支持短期事件跟进，避免旧报告看起来仍覆盖当前事实 | 基于新增可见记录；无新增记录不直接证明风险消失，不承诺客户端离线时监控 |
| 高校业务上下文 | P1：允许登记来源明确、适用范围和有效期清楚的实验授权、维护说明及业务背景 | 辅助解释告警和核查顺序，形成有依据的高校场景特点 | Wazuh 未提供时须由用户或另行授权来源补充；人工自述与已核实授权区分，不凭业务繁忙判为良性 |
| 近期案件回看 | P1：检索本机已保存、当前用户可访问的近期案件与审核结果 | 复用近期核查过程，说明本次与上次的相同点、差异和仍缺证据 | 只代表本机已记录范围；历史模型判断不自动升级为事实，也不声称全校历史完整 |
| 长期归因、跨部门多人协同、自动整改 | 暂缓 | 可能有后续价值，但涉及更多数据、共享服务和执行权限 | 不借客户端扩展重新引入完整安全运营平台 |

核查闭环需明确：模型提出“建议复查”，人工记录“已处理”，获准查询实际观察到变化，分别是三种来源与强度不同的信息。本地记录不能作为学校设备上动作已经生效的回执；在客户端中点“完成”也不代表远端威胁已消失。

建议首轮演示只验证 P0 这一条链：选择告警 → 建案 → 助手补证 → 展示支持、冲突与未知 → 人工确认 → 形成核查清单与处理记录。新增证据复核作为后续扩展，不同时承诺整张功能表。

TeleAgent 在这条链上承担有界的调查执行，调用本项目工具并给出带引用的分析草案；Node.js 应用承担业务状态、证据、界面和使用者操作。即使平台会话失效，已保存的案件与人工记录仍能查看和继续整理。

### 7.3 改写场景的完成条件

| 场景 | 拟调整后的验证重点 |
|---|---|
| 认证失败告警 | 能解释原告警依据、查询获准背景并说明覆盖；不要求客户端重新生成同等告警 |
| 失败后成功调查 | 有成功记录且身份、时间条件可确认时形成支持关系；缺少背景或权限时输出具体缺口 |
| 网络设备告警 | 区分签名命中、观察到的行为与攻击成功；只引用实际可见数据 |
| 资产与排序 | 缺业务重要性时允许只给基础调查顺序，拟处置建议保留人工核验条件 |
| 业务反证 | 只有来源明确的维护、授权或人工确认信息才可使用；缺失时不得用模型常识补齐 |

### 7.4 替换原主要验收口径

拟将原始日志 EPS、PCAP 处理速度、Wazuh 安装与规则输出移到实验平台附录。客户端主验收改为下列项目，并在正式设计时确定样本与阈值：

1. **接入真实边界**：仅使用受限账号，无服务器文件或管理凭据；面板可用但 API 不可用时正确报告接入限制。
2. **查询正确性**：分页、重复、迟到、部分结果、限流、断线恢复；失败批次不能误推进已完成位置。
3. **可见范围正确性**：权限受限时不输出全校结论；拒绝访问和没有匹配记录分别呈现；账号切换不串用案件与缓存。
4. **证据与结果正确性**：引用可定位到取得时的材料；本地快照与平台当前记录区分；旧结果不覆盖新证据；日志内指令不能成为新增权限或操作依据。
5. **TeleAgent 适配正确性**：提交、完成、重连和错误状态与实测协议一致；处理期间断线不盲目重复提交；真实文本轮次、模拟 MCP 链路与真实模型工具调查分列。
6. **部署可迁移性**：实验中把 Wazuh 与客户端放在不同主机或隔离环境，主流程仍成立；访问不到原始数据目录不影响受限查询流程。
7. **使用价值**：以相同的初始告警、可用数据和权限，比较现有面板人工核查、固定模板辅助与客户端调查流程；如要单独比较模型解释，再固定相同证据包。记录核查时间、无依据判断、重要信息遗漏、核查事项完成情况和建议可执行性；数据与评估真值隔离。

增加下游业务用例：调查中补入授权说明后如何调整解释；人工否定模型假设后如何保存修订；生成核查事项后是否仍保留未完成项；远端会话失败时本地案件是否可继续；再次查询出现冲突证据时是否提示复核。不得以工具调用次数更多或报告更长作为效果改善。

性能侧重点改为查询耗时、返回量与传输量、案件完成耗时、客户端资源、远端尝试与用量。平台本身检测性能不计为客户端成果。无法完成和证据不足的案件保留在统计中。
