# 任务与 Git 工作流程

日期：2026-10-23；协作规范 0.2。[任务模板](task-template.md) · [文件归属](ownership.md)。

## 领取与状态

初期以 docs/development/tasks 内的具体文件维护唯一任务状态。开始前填写任务、真实 base commit、依赖提交、允许路径、检查命令及外部操作范围；没有依据的任务保持 planned。

状态为 planned → ready → in_progress → checking → done。ready 要求基准可复现、依赖已合并、范围及验收明确；checking 表示正在自检或已完成但未合并；done 要求任务完成条件满足、检查与组合结果记录、成果已进入 main。blocked 写明具体阻塞与已完成内容；cancelled 保留原因。

PR 和另一成员/Agent 复核按需使用，不作为所有任务的固定门槛。任何未通过的真实链路不能因本地自检通过而标完成。

## 分支和目录

一条 main 主线、每个任务一个短分支，例如 task/T001-foundation。开始前查看 branch、HEAD 和未提交改动；不覆盖他人工作。并发任务使用独立 clone/worktree，不在同一目录并发切分支。顺序执行时也要保证工作目录干净再切换任务。

契约、DDL、锁、根配置、CI 及装配入口一次只由一个任务写入；其他任务可读，遇到缺口先记录影响，继续不依赖缺口的工作。Git 不提供业务文件写锁。

## 实现、自检与合并

完成者负责检查需求、修改路径、数据所有权、失败/未知语义和关键竞态，运行任务检查并记录结果。默认使用合成夹具，真实模型/平台试验另外记录当次授权。

合并前查看 main 的新提交，必要时在本任务分支合入并执行受影响的组合检查；通过后由完成者合并到 main。若使用 PR，可用模板汇总差异和验证，但无需另一账号批准。main 损坏时优先修复或回退具体变更，暂缓发出依赖任务。

## 交接

记录任务/版本/base、已合并提交、实际修改路径、已完成行为、检查命令及结果、未执行或失败原因、未提交内容和下一步。任务文件在后续提交中记录准确合并 commit；不把无法自引用的未来 commit 当作已有值。

对话形成长期决定后写入相应版本化文档；GitHub 接入后若改用 Issue 维护实时状态，在原任务文件明确指向唯一新位置。

## 四人工作线启动约定

当前入口见[任务登记](tasks/README.md)。四条分支分别对应唯一任务文件；用户只指定其中一个分支名时，Agent 按该文件执行，不必重新询问分工。先取得包含任务文件的 main 提交，使用独立目录创建分支，记录实际 base。登记的设计 base 用于追溯，不替代实际启动 commit。本文档分工更新不自动创建、提交或推送分支。

首阶段完成可独立合并；等待产品依赖时不通过复制契约或邻模块业务绕过。消费者记录依赖的准确已合并 commit 后再放行下一阶段。共享文件按本轮[归属](ownership.md)串行写入，合并由当次完成者负责。
